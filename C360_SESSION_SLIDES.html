Pick the engine by the question

Lightning Tables — what is true right now

  • Key lookups, filters and top-N on one table: “show me that customer”, “what just happened”.
  • Fresh in about a second (raw feed) to about a minute (Customer 360).
  • Console or CLI, the live front end over JDBC — or just ask your assistant, through the confluent-rtce MCP server.
SELECT full_name, kind, action, ts
FROM c360_live_activity
ORDER BY ts DESC LIMIT 5

Trino on Iceberg — what is true over time

  • Counts, sums, group-bys, joins and history: “how many…”, “which segment…”.
  • A few minutes behind; read-only through Polaris, in your own bucket.
  • Ask “how many?” of Lightning and the honest answer is: it can't aggregate — list the rows, or use Trino.
SELECT segment, count(*)
FROM polaris."lkc-817z505".c360_snapshot_prebuilt
WHERE risk_band = 'HIGH' GROUP BY segment
Same data product, two serving paths — chosen by the question, not by the tool.
11 / 15

The trade-off we accepted: exactly-once, up to a minute behind

  • Why it lags. A Flink statement writes to Kafka in transactions that commit about once a minute (exactly-once). Lightning Tables read only committed records, so every Flink hop adds 0–60 seconds.
  • What we measured. The raw event shows up in about a second; the Customer 360 row 33–68 seconds after the button press.
  • What we ruled out. Reading uncommitted data only helps Flink-to-Flink reads and can show duplicates; the commit interval is not configurable today. We will revisit when a shorter one is available.
  • What we did instead. Two speeds, said out loud: a lane with no Flink for “what just happened”, and the exactly-once Customer 360 row for “who is this customer”.
A faster Customer 360 row was not on offer — so the demo turns the delay into the point instead of hiding it.

What we'd tackle next

  • Wire up GitHub Copilot too — Confluent's MCP server works with Copilot too; add the project-level config so the same prompts drive the build from VS Code. (Claude Code and IBM Bob are wired by make up and make ai-bob.)
  • Put the live feed to work: point an agent at c360_live_activity through the confluent-rtce MCP server for “what just happened” alerts, not only questions.
  • Generate the Terraform for the use case itself — topics, schemas, tags, Flink jobs — by prompting the assistant, so it is reproducible on other environments.
  • Revisit the Customer 360 lag if a shorter Flink commit interval becomes available; until then the two-speed design keeps the demo honest.
  • Set a state TTL on the Flink rollup stages before scaling past demo volume — Flink flagged this itself during the first build.
  • Ingest credit-side transactions (salary, deposits, incoming transfers) so net_amount_30d reflects true cash flow, not just spend.
None of this is hypothetical — Tableflow, Trino, Lightning and the Bob wiring are already in place; these are the extensions.
